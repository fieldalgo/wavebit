Targets:

기존 공개 `wavebit.fdtd.native` 엔진으로 아래 사례의 Torch CUDA 배정밀도
실행과 eager 역방향 미분을 검증했습니다. 범위를 한정한 장치 검증
결과입니다. 일반 `wavebit.fdtd` 장면 API는
[별도의 제한된 CUDA 검증](general-cuda.md)을 참고하세요. [GPU의 JAX](#gpu의-jax)는 해당 절의 사례만 확인했습니다. 단정밀도, 컴파일 실행, 주기 구조의 포괄적인
CUDA 정확도는 이 문서의 검증 범위에 포함되지 않습니다.

## 환경과 재현

측정 기반은 Wavebit 0.0.4의 `2c04ccae`이며 위 테스트·연구 스크립트와
이 문서의 native 스펙트럼 좌표 장치 수정을 추가했습니다.
Windows 11 빌드 22631.6199, Python 3.12.14,
Torch 2.14.1+cu130, CUDA 런타임
13.0, NVIDIA 드라이버 610.88, AMD Ryzen 5 7500F(6코어 / 12스레드),
VRAM 8 GiB의 RTX 4060 Ti를 사용했습니다.
NumPy 2.5.4, SciPy 1.18.1, array-api-compat 1.15.0입니다. 한 장비의
측정 결과이며 여러 운영체제의 지원을 검증한 것은 아닙니다.

아래 24단계 크기 비교와 96단계 체크포인트 표는 **Bloch 인자 재사용 전**의
기준 측정을 보존합니다. 이후 최적화는 별도의 전후 비교에 기록했습니다.
현재 소스에서 재현 명령을 실행하면 같은 문제를 현재 구현으로 측정합니다.

체크아웃 전용 환경을 만들고 활성화한 뒤 CUDA wheel을 명시적으로 설치합니다.
PowerShell 예시는 다음과 같습니다.

```powershell
py -3.12 -m venv .venv
.venv\Scripts\Activate.ps1
python -m pip install torch==2.14.1 --index-url https://download.pytorch.org/whl/cu130
python -m pip install -e ".[pytorch]" pytest
python -c "import torch, wavebit; print(wavebit.__file__); print(torch.__version__, torch.version.cuda); print(torch.cuda.is_available()); print(torch.cuda.get_device_name(0))"
python -m pytest tests/fdtd/test_native_cuda.py tests/fdtd/test_native_cuda_admission.py -q
python studies/fdtd/native_cuda/native_cuda.py --sizes 8 16 32 64 --steps 24 --repeat 3 --output artifacts/native-cuda.json
```

다른 셸에서는 해당 셸의 가상환경 활성화 명령을 사용합니다.
[소스 체크아웃 안내](../../development/source-checkout.md)를 참고하세요.
`wavebit.__file__`이 현재 체크아웃을 가리키고 CUDA가 사용 가능한지 먼저
확인해야 합니다. Torch나 CUDA가 없으면 테스트를 건너뛰므로, skip은 GPU
실행 근거가 아닙니다. 생성된 JSON은 로컬 출력입니다. 원본 시간 측정 기록은
체크아웃에 배포하지 않으며 측정한 중앙값과 할당기 최대값을 아래에 옮겼습니다.

`native.run(problem, numerics=numerics, backend='torch', device='cuda:0')`를
사용하거나 `native.prepare`에 같은 백엔드와 장치를 전달합니다. 입력은
실행 장치로 변환되며 기울기는 원래의 리프 텐서에 연결됩니다. 단위와 배열 순서는
[native 격자 안내](../../guide/fdtd/native-grids.md)를 참고하세요.

## 수치 검증 범위

측정 장치에서 native CUDA 파일의 여덟 사례가 통과했습니다. 입력·장치
검사 파일의 이전 실행은 CPU/CUDA와 장치 독립 검사를 포함하여 21사례가 통과했습니다.
유한한 사례의 검증이며 모든 FDTD 기능을 GPU에서 검증했다는 뜻은 아닙니다.

| 사례 | 기준과 허용오차 |
| --- | --- |
| 균일 전도체, 일정한 전류, 11단계 | 독립 SI 사다리꼴 전도도 갱신식의 E와 변하지 않는 H; 상대 허용오차 `2e-14`; 출력 dtype과 장치 검사 |
| z CPML, Lorentz 극, 횡방향 Bloch 위상, 비균일 z 간격을 포함한 30단계 펄스 | NumPy CPU의 E/H, 분극, 기록 장, 원시 푸리에 장, 스펙트럼 파워와 비교; 각 물리량의 최대값으로 정규화한 무한대 노름 오차 `5e-12` 이하; 두 광원 진폭으로 prepared 실행 재사용 |
| 체크포인트 간격 32와 7, CPU·CUDA 리프의 광원 진폭 역방향 미분 | 최종 E 제곱합 목적함수의 정확한 이차 스케일링과 상대 `2e-12`, NumPy 중앙차분과 상대 `2e-7`; 기록을 꺼서 30단계 전체가 서로 다른 체크포인트 분할을 거침 |
| 기록한 E 목적함수의 광원 미분 | 기록을 켠 상태에서 정확한 이차 스케일링과 상대 `2e-12` |
| 유전율 대비, 진동자 세기, 횡방향 Bloch 위상의 역방향 미분 | NumPy 목적함수와 상대 `2e-12`; 간격 `1e-4`, `5e-5`의 영이 아닌 중앙차분과 상대 `2e-6` |
| 영·비영 Bloch 위상의 이산 진행파 | 37·513단계 후 독립 Yee 분산식과 시공간 엇갈림을 반영한 E/H 평면파; CPU·CUDA 상대 `3e-13` |
| 입력 검사와 관측 장치 | 사용 불가능한 CUDA, 잘못된 재료/CFL/PML 입력, 호환되지 않는 prepared 재사용 거부; check/prepare는 장을 진행하지 않음; 장·스펙트럼·기록 좌표, tail·validity 텐서는 실행 장치 유지 |

장치 검사에서 스펙트럼 값과 z 좌표는 CUDA인데 x/y 좌표는 CPU에 할당되는
문제를 찾았습니다. 좌표를 장과 같은 장치에서 구성하여 Yee 갱신식을
바꾸지 않고 결과 계약의 불일치를 고쳤습니다. 수정 후 CPU와 CUDA의
장치 배치 검사가 모두 통과했습니다.

E, H, 분극, 푸리에 파워는 SI 단위와 크기가 다릅니다. 따라서 각 물리량
전체의 기준 최대값으로 오차를 정규화하여 상쇄로 영에 가까워지는 성분도
포함합니다. 서로 다른 물리량에 하나의 절대 허용오차를 적용하지 않습니다.
기준이 모두 영이면 정확한 영을 요구합니다. CPU 일치는 장치별 차이를
찾고, 독립 전도도 갱신식과 광원 스케일링 항등식은 별도 기준을 제공합니다.
재료·Bloch 중앙차분은 이 이산 문제의 미분 검사이며 연속체 수렴 검증은 아닙니다.

### 더 긴 단일 모드 전파

이후 집중 실행은 16사례가 통과했습니다. 기존 37·513단계 CPU/CUDA 파동
여덟 검사, 새 CUDA 실행 길이 두 개, CPU 변이 대조군 여섯 개이며 관련 없는
입력 검사 13개는 선택에서 제외했습니다. 긴 실행은 16×2×2 주기 격자,
epsilon 2.4, mu 1.7, Bloch 위상 0.37의 복소 무손실 모드 하나를
4097·16385단계(약 101.68·406.66주기) 전파합니다. 기준은 E/H의 시공간
엇갈림을 반영한 독립 Yee 분산식입니다.

실행 전에 긴 시간의 허용 기준을 `B(N) = 3e-13 * max(1, N/513)`로
고정했습니다. 일관된 방향으로 누적되는 반올림 오차를 허용하는 수치적
선택이며 **엄밀한 부동소수점 오차 상한은 아닙니다**. 기존 37·513단계의
`3e-13` 검사는 그대로입니다. 원소별 장 비교는 상대 B, 절대 0을 사용하여
여기되지 않은 성분의 정확한 영도 유지합니다. 모드 계수는 초기 모드에 대한
투영입니다. 위상 오차 단위는 라디안, 진폭 오차는 `abs(abs(coefficient)-1)`,
비모드 잔차는 투영을 뺀 상대 L2 노름입니다. 상대 모드 에너지 변화의 허용값은
`2*B + B**2`입니다. 이 노름은 단일 복소 모드에 대한 것이며 임의의 엇갈린
상태 중첩에서 보존된다고 주장하지 않습니다.

| 항목 | 4097단계 | 16385단계 |
| --- | ---: | ---: |
| B(N) | 2.395906e-12 | 9.581871e-12 |
| E 최대값 정규화 장 오차 | 1.447407e-13 | 3.357500e-13 |
| H 최대값 정규화 장 오차 | 1.460854e-13 | 3.380075e-13 |
| E 모드 위상 오차 (rad) | 1.418865e-13 | 3.311240e-13 |
| H 모드 위상 오차 (rad) | 1.413869e-13 | 3.307354e-13 |
| E 모드 진폭 오차 | 2.331468e-15 | 1.132427e-14 |
| H 모드 진폭 오차 | 2.775558e-15 | 1.110223e-14 |
| E 비모드 잔차 | 2.964613e-15 | 4.913670e-15 |
| H 비모드 잔차 | 2.697725e-15 | 6.326759e-15 |
| 상대 모드 에너지 변화 | 4.996004e-15 | 2.242651e-14 |

CPU 대조군 여섯 개는 두 실행 길이에서 `1e-6` 위상·진폭·직교 성분 변이를
거부합니다. 위상 변이는 에너지와 진폭을 보존하므로 에너지만으로 충분하지
않음을 보여 줍니다. 위 값은 로컬 테스트 XML에서 옮겼습니다. no-grad로
장·스펙트럼·tail 이력을 요청하지 않았지만 엔진은 길이 N의 영인 complex128
drive 배열을 여전히 할당합니다(각각 약 64·256 KiB). 따라서 메모리는
O(grid + steps)이며 실행 길이에 무관하지 않습니다. 두 실행 길이는 CPML,
분산 매질, 임의의 모드나 일반적인 장시간 안정성을 검증하지 않습니다.

```sh
python -m pytest tests/fdtd/test_native_cuda_admission.py --run-slow -k "plane_wave_matches or long_native_wave or long_wave_acceptance" -q
```

### 별도의 주기 슬래브 검사

`test_periodic_cuda.py`에서 균일 슬래브의 위·아래 입사 CUDA 두 사례가
통과했습니다(전체 테스트 실행 246.21초). 진공 속 슬래브의 두께는 0.1 µm,
상대 유전율은 2.25이며 파장은 0.85, 0.90, 0.95 µm입니다. prepared
거친 격자의 간격은 1/30 µm, 실행 시간은 진공에서 0.90 µm 파장의 주기
55배입니다. R, T, 복소 s 반사는 NumPy CPU와 상대 `2e-12`, 절대
`1e-14` 안에서 일치합니다. 격자 간격을 절반으로 줄이면 독립 Airy 식과의
반사 오차 노름이 감소하며 각 세밀한 격자의 복소 반사가 절대 `0.005`
이내에 들어갑니다. 이 두 유한 슬래브 사례를 검증한 것으로, 수렴 차수,
패턴 구조·분산 재료의 정확도, 주기 구조 CUDA 미분을 검증한 것은 아닙니다.
관측·런타임 최적화 후 최종 광학 재검증에서도 같은 periodic 두 사례와
[일반 CUDA 슬래브 세 사례](general-cuda.md)가 함께 통과했습니다.

```sh
python -m pytest tests/fdtd/test_periodic_cuda.py --run-slow -q
```

### GPU의 JAX

`tests/fdtd/test_jax_gpu.py`는 위 두 절의 native 도체 점화식, CPML·분산·Bloch·
prepared 재사용 사례, 주기 슬래브를 같은 허용오차로 `backend='jax',
device='gpu'`에서 다시 실행하고, 광원 진폭 미분을 CPU의 JAX(상대 `1e-10`)
및 CPU 중앙 차분(상대 `1e-6`)과 비교하는 검사를 더합니다. 2026-10-19 main
`3f2ad839`에서 다섯 검사가 모두 71.46초에 통과했습니다. 같은 RTX 4060 Ti를
WSL2(Ubuntu 26.04 LTS, NVIDIA 드라이버 610.88)에서 Python 3.12.14, JAX 0.11.0,
`jax-cuda13-plugin` 0.11.0, NumPy 2.5.1, SciPy 1.18.0으로 사용했습니다. 확인한
결과 배열은 모두 GPU 장치의 complex128이었습니다. 측정 여유: 도체 장은 닫힌
식과 2.2e-16 이내, 분산 사례는 NumPy와 peak 정규화 5.4e-16 이내, 미분은 CPU와
같고 차분과 9.1e-13 차이, 슬래브 R, T, 반사는 허용오차의 0.4 % 이내, 세밀한
슬래브는 Airy 반사와 1.7e-3 이내입니다. 이 사례들만, 한 GPU에서 검증한
것이며 일반 `wavebit.fdtd` 장면 API의 JAX는 CPU만 허용합니다. CUDA를 지원하는
jaxlib이 없으면 건너뛰며, 건너뜀은 실행 증거가 아닙니다.

```sh
python -m pytest tests/fdtd/test_jax_gpu.py --run-slow -q
```

## 측정 비용

**Bloch 인자 재사용 전 기준:** 이 절의 두 표는 원래 측정값을 보존하며
최적화 이후의 시간이 아닙니다.

연구 스크립트는 정육면체 격자, 24단계, 진공 매질, 점 전류, 양쪽 z 끝의
CPML 2셀, float64/complex128, 체크포인트 간격 8을 사용합니다. CPML 폭은
비용 측정용 설정이며 반사 정확도를 위한 권장값이 아닙니다. 각 설정을 한 번
워밍업한 뒤 세 번 측정하며 CUDA를 각 측정 직전과 직후에 동기화합니다.
CPU Torch는 스레드 하나를 사용합니다. 역방향 행은 순방향 실행과 최종 E
제곱합의 광원 진폭에 대한 `autograd.grad`를 함께 측정합니다.

시간에는 실행 입력 구성, `native.run`의 준비·시간 진행·결과 구성과
목적함수 계산이 포함됩니다. 역방향 행에는 backward도 포함됩니다. 최초
고정 전류 밀도 텐서 할당·전송, 스칼라의 호스트 복사, JSON 기록, 워밍업은
제외합니다. 커널만의 시간이 아니라 eager 호출 전체 비용이며
`torch.compile`은 사용하지 않습니다. 순방향은 Torch gradient mode를 끄고,
역방향은 켭니다. CPU/CUDA 16행 모두 매 반복의 유한값, CPU/GPU 목적함수·
기울기 일치, 정확한 이차 광원 기울기 검사를 통과했습니다(상대 `2e-12`).

| 8³ | 순방향 + 역방향 | 0.055249 | 0.184646 | 0.30 | 0.631 / 2 |
| 16³ | 순방향 | 0.019155 | 0.039542 | 0.48 | 3.729 / 6 |
| 16³ | 순방향 + 역방향 | 0.078316 | 0.169783 | 0.46 | 4.814 / 6 |
| 32³ | 순방향 | 0.081851 | 0.037559 | 2.18 | 30.260 / 36 |
| 32³ | 순방향 + 역방향 | 0.279998 | 0.179967 | 1.56 | 38.783 / 58 |
| 64³ | 순방향 | 1.475292 | 0.057488 | 25.66 | 238.010 / 292 |
| 64³ | 순방향 + 역방향 | 4.233025 | 0.184147 | 22.99 | 306.033 / 372 |

작은 사례는 CUDA가 더 느렸고, 이 CPU 단일 스레드 비교의 32³ 및 64³
사례는 더 빨랐습니다. 다른 CPU 스레드 수, 격자, 실행 길이, 재료, 관측
설정, 정밀도의 속도를 이 비율로 예측할 수 없습니다.

할당기 최대값은 워밍업, 가비지 수집, 캐시 해제 이후 초기화하며, 살아 있는
입력 텐서를 포함한 세 번의 측정 전체를 집계합니다. 측정 전 baseline
allocated도 별도로 기록합니다(크기 8, 16, 32, 64에서 각각 12,288,
98,304, 786,432, 6,291,456바이트). allocated는 실제 텐서
할당량이고 reserved는 Torch 캐시 할당기가 확보한 메모리를 포함합니다.
두 값 모두 전체 GPU 프로세스·드라이버·화면 메모리는 포함하지 않습니다.
CPU 메모리는 측정하지 않았습니다. VRAM 8 GiB라는 사실만으로 더 큰 격자나
긴 역방향 실행이 들어간다고 판단할 수 없습니다. 체크포인트 간격, 관측
기록 보존, 재료 기억은 별도로 측정해야 합니다.

### 더 긴 실행과 체크포인트 간격

같은 64³ 설정을 96단계로 늘려 체크포인트 간격 8, 32, 96을 측정했습니다.
각 행은 한 번의 워밍업과 세 번의 동기화한 반복을 사용합니다. CPU/CUDA
12행 모두 해당하는 수치 검사를 통과했으며 모든 설정의 측정 전 live
CUDA 할당량은 6 MiB였습니다.

| 체크포인트 간격 | 모드 | CPU 중앙값 (초) | CUDA 중앙값 (초) | CUDA 최대 allocated / reserved (MiB) |
| --- | --- | ---: | ---: | ---: |
| 8 | 순방향 | 4.856461 | 0.213950 | 238.011 / 292 |
| 8 | 순방향 + 역방향 | 15.911914 | 0.741333 | 666.034 / 804 |
| 32 | 순방향 | 4.459965 | 0.215621 | 238.011 / 292 |
| 32 | 순방향 + 역방향 | 15.118165 | 0.729725 | 306.104 / 372 |
| 96 | 순방향 | 4.219480 | 0.215064 | 198.011 / 256 |
| 96 | 순방향 + 역방향 | 14.655525 | 0.711200 | 226.289 / 276 |

간격 8에서 24단계를 96단계로 늘리면 역방향 최대 allocated가 306.033에서
666.034 MiB로 증가했습니다. 이 96단계 설정에서는 더 큰 간격의 측정
최대값이 작았지만, 다른 실행 길이나 물리에서 최적 간격이라는 뜻은
아닙니다. 간격 96도 한 블록의 체크포인트 실행이며 체크포인트를 끄는
설정이 아닙니다. 이 측정은 장시간 안정성이나 VRAM 8 GiB 장비의 메모리
한계를 입증하지 않습니다.

```sh
python studies/fdtd/native_cuda/native_cuda.py --sizes 64 --steps 96 --checkpoint-steps 8 --repeat 3 --output artifacts/native-cuda-96-cp8.json
python studies/fdtd/native_cuda/native_cuda.py --sizes 64 --steps 96 --checkpoint-steps 32 --repeat 3 --output artifacts/native-cuda-96-cp32.json
python studies/fdtd/native_cuda/native_cuda.py --sizes 64 --steps 96 --checkpoint-steps 96 --repeat 3 --output artifacts/native-cuda-96-cp96.json
```

## 연산별 프로파일링

선택적인 프로파일링 도구는 실제 32³ 순방향, 64³ 순방향, 64³ 순방향·역방향
CUDA 실행을 완료했고 각 사례의 CUDA 활동을 수집했습니다.
CPU dispatch와 CUDA 활동의 shape·메모리를 기록하고 Chrome trace와 연산
표를 내보내며 실패해도 시도 기록을 남깁니다. 도구의 실행을 검증한 것이며
프로파일러 시간은 벤치마크 결과가 아닙니다. 포함 시간은 연산 간 겹칠 수
있고 shape·메모리 추적은 오버헤드와 텐서 수명을 바꿉니다. 시간을 합산해
전체 실행 시간으로 해석하거나 프로파일링 최대 메모리를 비계측 비용
연구의 값으로 대체하지 마세요.

```sh
python studies/fdtd/native_cuda/profile_native_cuda.py --size 32 --steps 24 --checkpoint-steps 8 --mode forward --device cuda:0 --output-dir artifacts/native-cuda-profile
```

매번 새 출력 폴더를 선택하세요. 기존 폴더를 덮어쓰지 않습니다. trace와
보고서는 로컬에서 생성됩니다.

### 미분 가능한 Bloch 인자 재사용

Native 코어는 호출마다 순방향·역방향 Bloch wrap 인자를 한 번 구성하여
해당 실행의 curl과 관측 보간에서 재사용합니다. 인자는 미분 그래프를
유지하며 매 호출의 live 위상으로 다시 계산합니다. 영 위상 전용 분기나
그래프에서 분리한 상수 캐시는 없습니다. 새 JAX 스캔 캐시 검사는 세 위상을
모두 바꾸어 프로그램 재사용을 확인하고 두 번째 호출의 E/H·푸리에 장이
새 위상에서 처음 컴파일한 결과와 바이트 단위로 일치함을 검사합니다.
관련 물리·미분 70사례, 기존 스캔 14사례, 이 새 사례가 통과했습니다.

별도의 시간 실험은 같은 24단계 문제, 체크포인트 간격 8, 한 번의 워밍업,
변경 전후 각각 **다섯 번**의 동기화한 반복을 사용했습니다. 순방향은
gradient mode를 끄고 CPU Torch는 스레드 하나를 유지했습니다. CPU/CUDA
모든 행이 해당 수치 검사를 통과했습니다. 아래 CUDA 값은 중앙값이며
대괄호는 관측한 최소–최대 범위입니다.

| 격자 | 모드 | 변경 전 (초) | 변경 후 (초) |
| --- | --- | ---: | ---: |
| 32³ | 순방향 | 0.034085 [0.031873–0.037173] | 0.029103 [0.028747–0.034839] |
| 32³ | 순방향 + 역방향 | 0.176703 [0.141419–0.195175] | 0.161988 [0.146971–0.209357] |
| 64³ | 순방향 | 0.058163 [0.056666–0.062642] | 0.056074 [0.055931–0.061953] |
| 64³ | 순방향 + 역방향 | 0.187348 [0.179126–0.193288] | 0.184639 [0.182334–0.204737] |

이번 중앙값은 줄었지만 전후 범위는 모두 겹치며 특히 역방향 변동이 큽니다.
한 장비의 다섯 번 반복은 보편적 성능 향상이나 통계적 신뢰구간을 입증하지
않습니다. 기록한 `grid.py` SHA-256은 변경 전
`c1dbb2967945d83918824177c9009cd443c6127bc961337976d1b8f197228742`,
변경 후
`5609d25df843e7e670ae2f426b2962939fb10164bb0b488733280ca3acc3d696`입니다.
도구는 새 측정마다 소스·스크립트 해시를 기록합니다.

별도의 32³ 순방향 trace에서 원시 CUDA 커널 이벤트는 2,420개에서
2,138개로, `aten::reciprocal` 호출은 148개에서 7개로 줄었습니다. 제거된
반복 작업의 수이며 실행 시간 추정값은 아닙니다. CUDA 커널 행과 CPU 연산
귀속은 같은 작업을 나타낼 수 있으므로 더해서 계산하면 안 됩니다.

```sh
python studies/fdtd/native_cuda/native_cuda.py --sizes 32 64 --steps 24 --checkpoint-steps 8 --repeat 5 --output artifacts/native-cuda-factor-reuse.json
```

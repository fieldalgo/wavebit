# JIT 경계를 가로지르는 구 자르기

작성일: 2026-09-21.

대상: `src/wavebit/fdtd/_shapes/_exact.py`, `tests/fdtd/test_fd_sphere_clip_jit.py`,
`tests/fdtd/test_fd_shapes.py`.

반지름 방향 거리의 제곱을 인수분해해 두면, 융합된 계산(fused computation)들 사이에서도 끝점의
부호가 안정적으로 유지됩니다. 이렇게 하면 보호된 제곱근의 비활성 값이 물리적 부피에 들어오지
않습니다. 32개 원점, 네 백엔드 관문은 적분 방법을 바꾸지 않고도 남은 채움 차이를 2.30e-13 미만으로
측정합니다.

## 재현 예제와 원인

2026-09-21에 Windows CPU 백엔드에서 전 과정 float64로 측정했습니다:
Python 3.12.14, NumPy 2.5.1, JAX/jaxlib 0.11.0, Torch 2.13.0+cpu.
`5fd02a4`의 형상 분기에 있는 결함은 평범한 해상도에서 나타납니다:
`Sphere(0.3)`, voxel 한 변 `0.05`,
`Box((0.2, 0.2, 0.9), angle=0.5)`. 16의 세제곱 격자는 -0.4에서 시작하고,
중심은 `-0.4 + (arange(16) + 0.5) * 0.05`에 있습니다. 원점 32개를
`default_rng(73).uniform(-0.5, 0.5, (32, 3)) * 0.05`로 스윕하되, 첫 번째 원점은 0으로 바꿉니다.

원점 26의 인덱스 `(8, 7, 1)`에 있는 실패 voxel은
`(0.00161135212954675, -0.02089849705058622, -0.3005275396021332)`를 중심으로 합니다.
상자가 이 voxel 전체를 포함하므로, 두 곡면의 교집합을 근사하지 않고도 세 CSG 답을
구 자체의 채움에서 알 수 있습니다.

| 양 | NumPy / eager JAX | 원래의 jit 컴파일된 CSG |
|---|---:|---:|
| 자식 구 채움 | 0.460806344307509 | -200.940388564916 |
| 상자와의 합집합 | 1 | -199.940388564916 |
| 상자와의 교집합 | 0.460806344307509 | -200.940388564916 |

원점 13의 인덱스 `(11, 7, 2)`는 양의 방향 이탈을 독립적으로 잡아냅니다:
Difference가 0.010556720698161 대신 142.652258838284를 읽습니다. 구만 따로 컴파일하거나
진단용 중간값을 추가로 반환하면 결함이 가려질 수 있습니다.
테스트는 실제 호출자가 하는 것처럼 점유도(occupancy) 호출 전체를 컴파일해야 합니다.

처음으로 잘못된 식은 `_wedge_integral`에 있던 예전 줄입니다:

```python
rest = _root(k2 - t * t, xp)  # t = min(z, sqrt(k2))
```

위쪽 끝점에서 이 식은 독립적으로 반올림된 두 제곱을 뺍니다. 근호 안의 값은 수학적으로 0이지만,
평가된 부호는 축약(contraction)과 재계산에 따라 바뀔 수 있습니다. `_root`는 비활성 제곱근을 무한대
미분으로부터 보호해야 하며, 이전에는 다음을 평가했습니다

```python
live = v > 0
where(live, sqrt(where(live, v, 1)), 0)
```

XLA는 보호된 제곱근과 그 바깥 선택을 서로 다른 융합 계산에 배치할 수 있습니다. 거기서 불안정한
근호 안의 값을 다시 평가하면 두 선택이 서로 다른 조건값을 얻을 수 있고, 그 결과 비활성 값 1이
결과에 들어갑니다. 이것은 float32 경로도, 여덟 꼭짓점 반올림 잔차도, NaN 전파도 아닙니다.
다음 인과 진단은 대수적으로 관측할 수 없는 값 하나만 바꿉니다:

| `_root`의 비활성 근호 안 값 | 원래의 jit 컴파일된 CSG에서 자식 구 채움 |
|---:|---:|
| 0.25 | -203.436302 |
| 1 | -200.940389 |
| 4 | -186.097088 |
| 0, 진단 전용 | 0.460806344308 |

0을 쓰면 보호 장치가 막고 있는 유한하지 않은 역방향 미분이 다시 돌아오므로, 0은 수정이 아닙니다.
fast math만 끄는 것으로는 이 예제가 고쳐지지 않았습니다.
최적화된 HLO 산술을 NumPy로 평가하면 0.460806344308이 나왔고,
백엔드 최적화 수준 0이나 융합을 끈 진단 컴파일도 같은 값을 돌려주었습니다. XLA_FLAGS는 설정하지
않았으며, 수정된 구현에는 컴파일러 설정이나 최적화 장벽이 필요하지 않습니다.

## 정확한 대수적 수정

적분 한계와 근호 안의 값에 같은 계산된 끝점 `k`를 사용합니다:

```python
k2 = (radius - a) * (radius + a)
k = _root(k2, xp)
t = minimum(z, k)
rest = _root((k - t) * (k + t), xp)
```

`t <= k`이므로 두 인수는 음이 아니며, 한계가 `k`와 같을 때 `k - t`는 정확히 0입니다.
이렇게 하면 결과 부피를 잘라 내거나(clamping) 적분 방법을 바꾸는 대신 불안정한 0 비교 자체가
사라집니다. 같은 인수분해를 `_arc_integral`과 꼭짓점의 반지름 방향 및 직사각형 전이 높이에도
사용합니다. 후자의 경우 `R^2 - a^2 - b^2 = (ka - b)(ka + b)`는 그 원시함수들이 보는 것과 같은
`ka`를 사용합니다. 모든 백엔드가 이 같은 식을 실행합니다.
양의 비활성 보호 값은 그대로 남아 있어 유한한 자동 미분을 보존합니다.
새로운 허용 오차, 하한, voxel별 예외, 백엔드별 경로는 없습니다.

이 수정은 불안정한 근호 안의 값을 다룹니다. 여덟 꼭짓점 누적 부피의 별도 반올림 예산은
기존 구 부피 테스트가 기록하는 대로 여전히 약 `eps * (R/h)^3`입니다. 이것은 임의로 큰 `R/h`에 대해
균일한 상대 정확도를 약속하는 것이 아닙니다. 앞서 `R/h = 262144`에서 했던 탐색은 다른 상쇄 영역이었고,
이 평범한 해상도 버그를 재현하지 않았습니다.

## 측정한 관문과 변이

새 관문은 NumPy, eager JAX, jax.jit, Torch에서 Sphere, Union, Intersection, Difference에 대해
32개 격자 원점을 모두 평가합니다: 격자 평가 512회이며, 각각 voxel 4096개입니다. 모든 결과는
float64 여부, 유한성, 채움 범위, 백엔드 간 일치, 법선 모멘트 범위와 대각합(trace), 정확한 CSG 포함 법칙을
검사합니다. 구는 추가로 모든 백엔드의 모든 원점에서 `4*pi*R^3/3`을 재현해야 합니다.
기존의 독립적인 적응형 원판 구적법과 그래디언트 테스트는 계속 활성 상태입니다.

| 수정된 식, 전체 스윕 | 측정된 최악값 | 테스트 허용 오차 |
|---|---:|---:|
| NumPy 대비 절대 채움 차이 | 2.30e-13 | 1e-12 |
| [0, 1] 밖으로의 채움 이탈 | 2.78e-14 | 1e-12 |
| 절대 법선 모멘트 차이 | 2.71e-14 | 1e-13 |
| 구 전체 부피의 상대 오차 | 1.67e-15 | 1e-14 |

이 허용 오차들은 스윕 이후에 정했으며, 측정된 여유도 테스트의 상수 옆에 적어 두었습니다.
두 번째 테스트는 양의 비활성 근호 안의 값을 0.25, 1, 4로 바꾸어 가며 각 값마다 새로운 전체 CSG 호출을
컴파일합니다.

소스 변이를 적용하고, 종료 코드로 판정한 뒤, 원래대로 되돌렸습니다:

1. `_exact.py`에서 원래의 제곱 뺄셈 식을 되살린 다음
   `python -m pytest tests/fdtd/test_fd_sphere_clip_jit.py -k "jax.jit or inactive_root" -q`를 실행했습니다.
   선택된 두 테스트 모두 정상적으로 실패했습니다: exit 1, 2 failed, 3 deselected. 감시(sentinel)
   단언은 0.46080634430750905 대신 -203.43630164659726을 보고했습니다.
2. 구가 반환하는 부피에 0.99를 곱한 다음
   `python -m pytest tests/fdtd/test_fd_sphere_clip_jit.py -k across_grid_origins -q`를 실행했습니다.
   네 백엔드 경우 모두 해석적 부피 단언에서 실패했습니다: exit 1, 4 failed,
   1 deselected. 범위 검사와, 똑같이 변이된 NumPy 기준과의 일치 검사는 여전히
   통과했습니다. 공유 구현과의 일치만으로는 판정 기준(oracle)이 되지 않습니다.

추가로 잘못된 원시함수 변이(`z**3 / 3` 대신 `z**3 / 2`)도 네 백엔드 경우 모두 채움 범위에서
실패했습니다. 다른 전이 높이들을 인수분해한 뒤 쐐기(wedge)의 인수분해하지 않은 `k2 - t*t`만
되살렸을 때는 이 샘플들에서 원래 결함이 재현되지 않았습니다. 그래서 회귀 변이에서는 예전 식을
통째로 되살렸습니다. 반대로, 원래 식에서 쐐기 끝점만 인수분해해도 고립된 실패 voxel을 고치기에는
이미 충분했습니다.

전체 스위트와 고정된 기준 검사 전에 변이는 원래대로 되돌립니다.
